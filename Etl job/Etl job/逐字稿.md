## 1.背景與任務目標

各位好，今天想跟大家分享一下，近期做的一個 ETL 重構任務。
主要是把原本 PQO-PDMEtl 這個 repo 裡面用 Spring Batch 實作的 ETL 任務， 遷移到 PQO-batch 這個 repo，並改成用 Airflow DAG 來進行實作。

此次重構的核心，並不是單純把 Java 改成 Python，而是將 ETL 從「一個要被啟動的程式」，變成「排程系統裡的一個任務」。

也就是說，原本是到時間後，先啟動一個 Spring Boot application，再由裡面的 Spring Batch 去執行 ETL。

現在改成 Airflow 後，是由既有的排程系統直接去觸發一個 task，來完成整個 ETL 的資料處理流程。

## 1.1 任務範圍

此次重構任務主要涵蓋以下三張目標表的 ETL：

資料來源都是 PDM API，目標端都是 Oracle DB。

## 1.2 ETL 流程概念

如果用一句話描述這次的 ETL，其實非常單純：

就是 call PDM API，將取得的資料經過轉換之後，寫進 Oracle DB 裡的目標表。

這三個 ETL 任務有以下幾個共同特性：

第一，它們都是由 API 全量取得資料，也就是一次拿回完整資料。
第二，資料量其實不大。
第三，採用的是 Full Load。
第四，目標就是整批成功，不然就整批 rollback。
所以其實不需要太複雜的 partition、parallel processing，或者 incremental load 等策略。

## 1.3 本次分享重點

接下來的內容會分幾個部分來講。
首先會先講原本 Spring Batch 的架構與限制，
接著講本次重構的動機與目標，
再來介紹新的 Airflow DAG 架構與核心實作方式，
最後再分享這次改動完成之後的效益，以及設計上的一些取捨。

## 2. 原有系統設計（Spring Batch）

接下來先看原本系統的設計。

原本的 PQO-PDMEtl 是一個 Spring Boot 加 Spring Batch 的專案，

整體流程可以簡單理解成：
時間到了之後，K8s CronJob 會啟動 Spring Boot application，
再由 Spring Boot 裡面的 Spring Batch 執行 ETL，
最後把資料寫進 Oracle DB。

也就是說，原本的 ETL 是包在一個 Spring Boot application 裡面執行，
比較像是一個「被排程啟動的應用程式」。

## 2.1 / 2.2 專案結構與 Spring Batch 分層

從專案結構可以看到，
原本系統是典型的 Spring Batch 分層設計。

每一張表大致都會有自己的 Reader、Processor、Writer 等檔案。

Reader 負責呼叫 PDM API 取得資料，
Processor 負責欄位轉換與資料清洗，
Writer 則透過 DAO 或 JPA repository 寫入 Oracle。

另外還會有 model、repository、config 這些 layer，
例如 JPA entity、API 回傳的 TO、DB repository，
以及 PDMConfig、PQOConfig 這些設定檔。

以 TI_PROC_OPT 為例，
就同時需要 Reader、Processor、Writer 這些檔案，
最後再由 BatchConfig 組裝成 Step 跟 Job。

這種分層模式本身沒有問題，
在大型批次任務中可以讓責任切分很清楚。

但對本專案來說，
ETL 本質其實就是 call API、transform、insert DB。

所以在這個情境下，
一個相對單純的 ETL 仍然需要拆成多個 class，
也增加了理解與維護成本。

## 2.3 / 2.4 原系統架構與執行流程

這張圖主要是把剛剛提到的角色串起來。

從 runtime 的角度來看，原系統不是直接執行一段 ETL script，
而是先由 CronJob 透過 java -jar 啟動整個 Spring Boot application。

接著 Spring Boot 會建立 application context，
初始化 API client、DB connection、transaction manager，
以及 Spring Batch 需要的 Job、Step、Reader、Processor、Writer。

等這些元件都建立完成後，
Spring Batch 才會依照 BatchConfig 定義的流程開始執行 Job。

所以這裡想強調的是：
原本 ETL 的執行，需要先啟動完整的 Spring Boot application，
而不是 Airflow 裡可以直接管理的一個 workflow task。

## 2.4.1 Job 執行模式

接著補充一下 Job 的執行模式。

在原本的 Spring Batch 架構中，
系統裡定義了多個 Job，
分別對應不同的 ETL 任務。

當 Spring Boot application 啟動後，
這些 Job 會由 Spring Batch 自動執行。

這裡有幾個特性。
第一，在原設計中，Job 之間是同步執行，不是平行執行。

第二，Job 的執行順序主要由 Spring container 決定，
在原設計中沒有特別明確控制。

第三，如果錯誤沒有被妥善處理，
或是錯誤發生在 application / Bean 初始化階段，
就可能導致整個 application 結束，
進而影響後續 Job 的執行。

所以雖然這些 ETL 在邏輯上是不同的 Job，
但實際上它們仍然綁在同一個 application process 裡面執行，
並不是彼此完全獨立的任務。

## 2.4.2 Transaction 行為補充

最後補充 transaction 的部分。

在這個專案中，PQOConfig 有定義 JPA transaction manager。

所以當 Spring Batch Step transaction 內發生 exception 時，
Spring Batch 會 rollback 該 transaction。

但原本設計中有一個比較需要注意的地方。
在 Reader 裡面，deleteAll() 是放在 @PostConstruct 初始化階段執行。

也就是說，
Reader 在初始化時會先 call API，
把資料放進一個 list 裡。

如果 API 回傳的資料不是空的，
程式會先執行 dao.deleteAll()，
把目標表舊資料刪掉。

後續真正的 read()，
其實只是從前面已經取得的 list 裡面，
一筆一筆把資料吐給 Spring Batch。

這裡的問題是：
deleteAll() 發生在 Reader 初始化階段，
而不是在 Step transaction 裡面，
跟後續 insert 不在同一個 transaction 邊界。

所以會形成一個風險：

delete 已經先執行了，
但後面的 insert 如果失敗，
Step transaction 雖然會 rollback，
但前面已經執行的 delete 不一定會一起被 rollback。

這就可能造成一種狀況：

舊資料已經被刪掉，
但新資料沒有成功寫入。

也就是說，
原本的 delete 跟 insert 並沒有完整包在同一個 atomic transaction 裡面，
因此存在資料不一致的風險。

這也是這次重構希望改善的地方之一。

## 3. 原系統設計特性與實際使用情境

## 3.1 Spring Batch 的典型能力

Spring Batch 本身是一個功能完整的 batch framework，
所以這邊先簡單帶過它常見的幾個批次處理能力。

例如 chunk-based transaction，
可以用 chunk 作為 transaction 或 commit 的邊界。

另外，Spring Batch 也提供 retry / skip 機制。

除此之外，Spring Batch 也支援 partition 或 parallel processing，
可以把資料切分後平行處理，
提升大量資料的處理效率。

## 3.2 本專案對 Spring Batch 能力的實際使用情況

但回到本專案來看，
我們的 ETL 情境其實相對單純。

資料來源是 PDM API。

每次執行時，是由 API 全量取得資料。

單次資料量也不大。

整體流程主要就是：
call API、transform，然後 insert DB。

而且在資料一致性上，
我們希望的是整批成功，或是整批 rollback。

也就是說，
我們不希望出現部分資料成功、部分資料失敗，
或是部分資料被 skip 掉但整體仍然被視為成功的狀況。

所以雖然原系統使用 Spring Batch，
但 Spring Batch 一些比較典型的大批次處理能力，
在這個專案裡其實沒有被充分發揮。

## 3.3 Chunk-based Transaction 在本專案中的限制

接下來看 chunk-based transaction。

在 Spring Batch 裡面，
常見的做法是設定一個 chunk size。

例如 chunk size 設成 100，
代表 Spring Batch 會透過 Reader 一筆一筆讀資料，
經過 Processor 處理後，
累積到 100 筆時，再交給 Writer 寫入，
並 commit 這一個 chunk 的 transaction。

簡單來說就是：

read 和 process 累積 100 筆，
然後 write 100 筆，
最後 commit。

在本專案裡，Reader 會先從 PDM API 全量取得資料，
後續再透過 read() 一筆一筆交給 Spring Batch。

這種 chunk-based transaction 的設計在大量資料情境下很有價值。

但本專案資料量小，
而且我們希望整批成功或整批 rollback，
所以在這個情境下能帶來的效益就比較有限。

## 3.4 Retry / Skip 與本專案資料一致性需求

再來看 retry / skip。

Spring Batch 提供 fault-tolerant 機制，
可以針對特定 exception 設定 retry 或 skip。

例如某筆資料處理時發生特定錯誤，
可以設定先重試幾次。

如果仍然失敗，
也可以設定在符合條件時略過該筆資料，
繼續處理後面的資料。

這個機制在某些大量資料處理情境很有用。

例如資料中可能有少數 dirty data，
而業務上可以接受少數資料被略過，
不要因為單筆資料錯誤就讓整個批次中止。

但本專案的需求不是這樣。

我們比較重視的是資料一致性。

也就是說，
我們不希望出現「部分資料成功、部分資料被 skip」的結果。

所以 retry / skip 雖然是 Spring Batch 很重要的能力，
但它並不符合本專案希望整批成功或整批 rollback 的處理策略。

## 3.5 小結

所以綜合來看，
Spring Batch 本身沒有問題。

它是一個成熟的 batch framework，
也提供很多適合大型批次處理的能力。

但以本專案來說，
這些能力並沒有被充分使用。

這就形成一個狀況：

框架能力大於實際需求。

也就是說，
原系統為了使用 Spring Batch，
需要引入 Reader、Processor、Writer、Job、Step 等抽象層與設定。

但實際 ETL 流程本身相對簡單。

因此，對本專案而言，
整體架構就顯得比較重，
也增加了理解與維護成本。

## 4. 重構動機與目標

## 4.1 重構動機

這次重構主要想改善三個問題。

第一個是架構偏重。

原本需要先啟動 Spring Boot application，
再透過 Spring Batch Job 執行 ETL。

但實際流程其實就是 打API、transform、寫入DB。

第二個是維護成本。

原系統依賴 Spring Boot、Spring Batch、JPA 等 framework。

所以在版本升級、相依套件調整，
或 CI pipeline 維護上，
都會有比較多額外成本。

第三個是 log 過多且分散。

原系統裡面會同時有 framework log、application log，
以及 Kubernetes 執行相關的 log。

所以當任務異常時，
可能需要同時確認多個地方。增加排查問題的成本。

## 4.2 重構目標

因此，這次重構主要有幾個目標。

第一，簡化架構，
讓 ETL 實作更貼近打 API、transform、寫入 DB 的實際流程。

第二，降低維護成本，
減少 framework 升版、相依套件和 CI 維護負擔。

第三，統一排程管理，
把 scheduling、retry、monitoring 集中到 Airflow。

第四，整合排程相關程式。
將原本一些分散在不同 repo 的批次程式整合到一個repo中，方便後續追蹤管理。

## 4.3 架構轉變

最後用一句話看架構轉變。

原本是：

Kubernetes CronJob 啟動 Spring Boot application，
再由 Spring Batch 執行 ETL。

轉變成：

Airflow DAG 直接觸發 Python task，
再由 Python task 呼叫共用 ETL function。

所以這次改動的本質是：

ETL 不再需要透過啟動完整 application 來執行，
而是變成 Airflow workflow 裡可以被排程、重試、監控的一個 task。

## 5. 新系統架構（Airflow DAG）

接下來本節主要說明重構後的新系統架構。
包括新的 Airflow DAG 是怎麼設計，以及程式結構是怎麼拆分的。

## 5.1 新系統設計概念

重構後的 ETL，會被整合到 PQO-batch 這個 repo 裡面。

新的設計是以 Airflow DAG 作為主要的排程與執行單位。

這邊採用的是一張目標表對應一個 DAG 的設計。

目前有三個 DAG，
分別對應三張 target table。

每個 DAG 主要負責幾件事情。

第一，定義排程時間。
第二，定義 task 以及 retry 設定。
第三，指定這支 ETL 需要用到的 API endpoint、target table、
transform function，以及 insert SQL generation function。
最後，DAG 會透過 PythonOperator，
呼叫共用的 pdm_api_full_load_task，
由這個共用 function 完成實際的 ETL 流程。

## 5.2 新系統專案結構

接著看新系統的專案結構。

這次重構後，主要的 DAG 定義與共用 ETL 程式都放在 app/dags 底下。

可以大致分成幾類。

第一類是 DAG 定義檔。
這三個檔案分別對應三張 target table，
主要負責定義各自的 DAG、schedule、task，
以及跟該 table 相關的轉換邏輯。

第二類是共用 ETL 流程。
這部分主要放在 pdm_api_etl_utils 裡面的
pdm_api_full_load.py。

這個檔案是這次重構後比較核心的共用邏輯。

它會負責把 API full load 的共用流程封裝起來，
例如呼叫 PDM API、
將資料轉成 DataFrame、
執行 transform、
產生 INSERT SQL、
控制 DELETE 加 INSERT 的 transaction，
以及寫入 ETL control log 和 performance log。

第三類是 SQL 工具。

像 sql_utils.py，
主要提供 SQL 組裝相關的共用方法。

最後是 schemas.py 和 utils.py。

這些檔案主要放 schema、欄位定義，
以及其他共用工具。

補充一下，
在這個設計裡，
每個 DAG 檔案只保留跟該 table 有關的設定與邏輯。

例如 DAG name、schedule、PDM API endpoint、
target table、transform function，
以及 insert SQL generation function。

而真正共用的 ETL 流程，
則集中在 pdm_api_full_load.py 裡。

這樣做的好處是，
如果未來有新的 API full load ETL，
只要新增一個 DAG 檔案，
並指定對應的 endpoint、table 和轉換邏輯，
就可以複用同一套共用流程。

## 5.3 新系統架構圖

最後用架構圖來看整體流程。

Airflow Scheduler 會依照 DAG 的 schedule 觸發 DAG。

DAG 裡面會透過 PythonOperator，
呼叫 pdm_api_full_load_task。

接著 pdm_api_full_load_task 會執行主要 ETL 流程。

流程包含：

先呼叫 PDM API 取得資料。

接著進行資料轉換。
再產生 INSERT SQL。
然後進入 DELETE 加 INSERT 的 transaction control。

最後把資料寫入 Oracle DB。

另外，在執行過程中，
也會寫入 performance log。

如果發生錯誤，
也會寫入 control log，
方便後續追蹤問題。

6. 核心實作方式

接下來這一章，我會講比較偏實作面的設計，
也就是這次 ETL 在 Airflow 上是怎麼落地的。

6.1 一表一 DAG

第一個設計是「一張表對應一個 DAG」。

也就是說，每一個 ETL 任務，都有自己獨立的一個 DAG。

像是：

TI_PROC_OPT 對應一個 DAG
TI_RAW_WAFER_QUES 對應一個 DAG
TI_WF_OPT_CATG 對應一個 DAG

👉 這樣做有幾個好處：

第一個是 失敗隔離很清楚

某一個 ETL 壞掉，不會影響其他的。

第二個是 可以單獨 rerun

如果某一張表有問題，只需要 rerun 那一個 DAG 就好。

第三個是 排程跟 retry 可以分開調整

不同 ETL 可以有不同 schedule，也可以有不同 retry 策略。

6.2 共用 ETL Framework

第二個設計是，我們沒有把三個 ETL 各自重寫一份。

而是把共通邏輯抽出來，做成一個共用的 ETL framework，
也就是 pdm_api_full_load_task()。

整個流程其實很單純：

👉 先抓資料 → 做轉換 → 產生 SQL → 刪舊資料 → 寫新資料 → 記錄 log

👉 這樣設計的好處是：

所有共同行為都集中在同一個地方管理。

所以每個 DAG 只需要關注：

👉「這張表的資料怎麼轉」
👉「SQL 長怎樣」

未來如果再新增類似的 ETL，
基本上只要複製一支 DAG，再補上 transform 跟 SQL function 就可以了。

6.3 Full Load + Atomic Transaction

第三個設計是資料寫入策略。

這邊我們沿用原本的 Full Load，也就是：

👉 先 DELETE，再 INSERT

但這次有特別強調一件事：

👉 整個過程要包在同一個 transaction 裡面

也就是：

刪除成功、插入也成功 → 才 commit
只要中間有任何一步失敗 → 就全部 rollback

👉 這樣可以確保資料不會出現：

刪掉了，但新資料沒寫進來
或是只寫了一部分資料的狀況

換句話說，就是保證資料的一致性。

6.4 Airflow Retry 機制

再來是 retry。

在原本的 Spring Batch 裡，其實沒有明確用 retry / skip。

但在 Airflow 裡，我們可以直接在 task level 設定 retry。

像這裡設定：

最多 retry 5 次
每次間隔 10 秒
並且會做 exponential backoff

👉 這樣的好處是：

如果遇到像 API 暫時 timeout、或網路不穩這種「暫時性問題」，
Airflow 會自動幫我們重試，不需要人工介入。

不過這裡要注意，Airflow 的 retry 是 task-level retry。

也就是說，如果這個 task fail，Airflow 會重新跑整個 ETL task，
不是像 Spring Batch retry / skip 那樣，只針對單一 item 做 retry 或 skip。

所以這邊的 retry 比較適合處理 API timeout、網路不穩這種暫時性問題。

6.5 ETL 控制與績效記錄

除了 Airflow 自己的 log 之外，
我們還額外寫了兩張 DB log table。

第一張是 PERF_LOG

主要記錄整個 ETL 的執行情況，例如：

跑多久
處理幾筆資料
成功或失敗

第二張是 CTRL_LOG

這張比較偏錯誤細節，會記錄：

哪一筆資料出錯
錯在哪裡
error code 是什麼

👉 這樣的好處是：

即使不看 Airflow log，
也可以直接從 DB 查到 ETL 的執行情況與錯誤資訊。

6.6 小結（流程）

最後用一個流程來總結整個 ETL 的執行方式。

整體流程是這樣：

一開始先 call API，
如果沒有資料，就直接寫一筆 perf log 結束。

如果有資料，就會進入：

👉 transform → 產生 SQL → 開 transaction

接著會先做 DELETE，
如果 DELETE 失敗，就會：

👉 寫 ctrl log → rollback → 寫 perf log → task fail

如果 DELETE 成功，就會做 INSERT，
如果 INSERT 過程中有任何一筆失敗，也會走同一條錯誤流程。

只有在全部 INSERT 成功的情況下，才會 commit，
然後寫 perf log，整個流程才算完成。

👉 所以整體可以理解成：

正常流程走 commit，
錯誤流程全部集中 rollback + logging。

所以整個設計的重點，就是把正常流程跟錯誤流程都明確定義出來，並確保資料一致性。

7. 設計亮點與實際收益
7.1 架構簡化

第一個很直接的收益就是架構簡化。

原本的 Spring Boot application、Spring Batch Job / Step 組裝、
Reader / Processor / Writer、JPA entity / repository 依賴，現在都不需要了。

也就是說，我們把很多「為了框架而存在的結構」拿掉了，
讓程式更貼近實際需求。

7.2 維護成本下降

第二個是維護成本下降。

不是說 Airflow / Python 就完全沒有 CI 或 dependency 問題，
因為 DAG parsing、provider 相容性、pipeline 還是可能要修。

但相較於原本 Spring Boot 版本，
現在少掉了很多應用框架層級的建置、打包與升版負擔。
維護焦點會更集中在 DAG 跟 ETL 邏輯本身。

7.3 可觀測性提升

第三個是可觀測性提升。

現在透過 Airflow UI，可以直接看到：

DAG 有沒有成功
哪個 task fail
retry 幾次
log 是什麼

查問題會直覺很多。

7.4 可擴充性提升

第四個是可擴充性提升。

這次把共用流程抽成 framework，
所以未來若有更多類似 PDM API 到 Oracle 的 ETL，
可以比較快地複製與擴展。

7.5 Failure Isolation（失敗隔離）

第五個是 failure isolation。

如果錯誤是發生在 Step 裡，而且有被 Spring Batch 正常處理，
不一定會讓整個 application 中斷。

但如果是未處理的 exception，或是發生在 application 初始化階段，
就有可能讓整個 application 中斷，進而影響後續 Job。

所以我這邊會說，原本多個 ETL Job 不是完全隔離，
它們還是綁在同一個 application process 裡。

8. Trade-off 與設計取捨
8.1 SQL 執行策略：row-by-row

第一個 trade-off 是 SQL 執行策略。

目前採用 row-by-row，也就是逐筆執行 INSERT SQL。

原因很簡單：資料量小、邏輯直觀，
也方便記錄單筆錯誤與 control log。

但代價就是 DB round trip 會比較多。
如果未來資料量明顯增加，就可以評估 batch insert、parameterized SQL 或 executemany。

8.2 資料同步策略：Full Load

第二個 trade-off 是資料同步策略。

目前採用 Full Load，也就是 DELETE + INSERT，而不是 incremental load。

原因是 API 現在只提供全量資料，沒有提供 update timestamp 或 CDC。
如果硬做 incremental，反而要自己比對 diff，系統會更複雜。

所以在目前這個條件下，Full Load 其實是比較合理、也比較穩定的做法。
未來如果 API 能提供變更追蹤資訊，或者資料量顯著增加，再來考慮 incremental load 會比較有價值。

8.3 DAG 設計：單 task 模式

第三個 trade-off 是 DAG 設計。

目前每個 DAG 只有一個 PythonOperator，也就是單 task 模式。

這樣做的原因是，現階段流程很單純：
單一 API、單一 table、沒有中間層，也沒有複雜的 downstream dependency。

如果現在就把 DAG 拆成很多 task，
反而會增加 task 間資料傳遞、DAG 複雜度，以及 transaction 邊界管理難度。

但如果未來流程變複雜，例如加入 data validation、stage table、notification、data quality check，
那就可以再拆成 extract、transform、load、notify 等多個 task，
進一步提升可觀測性跟錯誤隔離能力。

9. 重構前後比較

如果用一句話總結這張比較表：

原本是 CronJob 啟動應用程式，
現在是 Airflow 直接執行任務。

技術棧從 Java / Spring Boot / Batch / JPA，
變成 Python / Airflow。

架構複雜度下降，維護成本下降，可觀測性由分散變集中。
retry 管理也從原本不明確，變成 Airflow 內建。
release unit 也從原本比較分散，變成集中在 batch repo 與 DAG。

10. 結論
10.1 本次重構帶來的效益

最後做個總結。

這次重構成功把原本 PQO-PDMEtl 的 ETL 流程，從 Spring Batch 架構搬到 Airflow DAG。
這次改造真正的價值，不只是技術棧從 Java 變 Python，
而是把 ETL 從「應用程式導向的批次程式」，轉成「排程系統導向的資料流程」。

這次重構帶來的效益包括：

維護成本下降、架構簡化、可觀測性提升、排程與任務管理整合、
同時保留既有 Full Load 與資料一致性策略，也提升了未來擴充與複用能力。

10.2 最後總結

所以對這種：

資料量小、Full Load、流程單純，而且需要排程與監控整合的 ETL 任務來說，
我認為 Airflow DAG 比 Spring Batch 更符合實際需求，
也更適合作為部門內類似批次任務的實作模式。

我的分享大概到這邊，謝謝大家。
