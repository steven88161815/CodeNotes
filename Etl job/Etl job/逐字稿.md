## 1.背景與任務目標

各位好，今天想跟大家分享一下，近期做的一個 ETL 重構任務。
主要是把原本 PQO-PDMEtl 這個 repo 裡面用 Spring Batch 實作的 ETL 任務， 遷移到 PQO-batch 這個 repo，並改成用 Airflow DAG 來進行實作。

此次重構的核心，並不是單純把 Java 改成 Python，而是將 ETL 從「一個要被啟動的程式」，變成「排程系統裡的一個任務」。

也就是說，原本是到時間後，先啟動一個 Spring Boot application，再由裡面的 Spring Batch 去執行 ETL。

現在改成 Airflow 後，是由既有的排程系統直接去觸發一個 task，來完成整個 ETL 的資料處理流程。

此次重構任務主要涵蓋以下三張目標表的 ETL：

資料來源都是 PDM API，目標端都是 Oracle DB。

## 1.2 ETL 流程概念

如果用一句話描述這次的 ETL，其實非常單純：

就是 call PDM API，將取得的資料經過轉換之後，寫進 Oracle DB 裡的目標表。

這三個 ETL 任務有以下幾個共同特性：

第一，它們都是由 API 全量取得資料，也就是一次拿回完整資料。
第二，資料量其實不大。
第三，採用的是 Full Load。
第四，目標就是整批成功，不然就整批 rollback。
所以其實不需要太複雜的 partition、parallel processing，或者 incremental load 等策略。

## 2. 原有系統設計（Spring Batch）

接下來先看原本系統的設計。

原本的 PQO-PDMEtl 是一個 Spring Boot 加 Spring Batch 的專案，

整體流程可以簡單理解成：
時間到了之後，Kubernetes CronJob 會啟動 Spring Boot application，
再由 Spring Boot 裡面的 Spring Batch 執行 ETL，
最後把資料寫進 Oracle DB。

也就是說，原本的 ETL 是包在一個 Spring Boot application 裡面執行，
比較像是一個「被排程啟動的應用程式」。

## 2.1 / 2.2 專案結構與 Spring Batch 分層

從專案結構可以看到，
原本系統是典型的 Spring Batch 分層設計。

每一張表大致都會有自己的 Reader、Processor、Writer。

Reader 負責呼叫 PDM API 取得資料，
Processor 負責欄位轉換與資料清洗，
Writer 則透過 DAO 或 JPA repository 寫入 Oracle。

另外還會有 model、repository、config 這些 layer，
例如 JPA entity、API 回傳的 TO、DB repository，
以及 PDMConfig、PQOConfig 這些設定檔。

以 TI_PROC_OPT 為例，
就同時需要 Reader、Processor、Writer等檔案，
最後再由 BatchConfig 組裝成 Step 跟 Job。

這種分層模式本身沒有問題，
在大型批次任務中可以讓責任切分很清楚。

但對本專案來說，
ETL 本質其實就是 call API、transform、insert DB。

所以在這個情境下，
一個相對單純的 ETL 仍然需要拆成多個 class，
也增加了理解與維護成本。

## 2.3 / 2.4 原系統架構與執行流程

這張圖主要是把剛剛提到的角色串起來。

實際執行時，
Kubernetes CronJob 會先透過 java -jar 啟動 Spring Boot application。

接著 Spring Boot 會建立 application context，
初始化 API client、DB connection、transaction manager，
以及 Spring Batch 需要的 Job、Step、Reader、Processor、Writer。

等這些元件都建立完成後，
Spring Batch 才會依照 BatchConfig 定義的流程開始執行 Job。

所以這裡想強調的是：
原本 ETL 的執行，需要先啟動完整的 Spring Boot application，
再由裡面的 Spring Batch 去跑實際的 ETL 流程。

## 2.4.1 Job 執行模式

接著補充一下 Job 的執行模式。

在原本的 Spring Batch 架構中，
系統裡定義了多個 Job，
分別對應不同的 ETL 任務。

當 Spring Boot application 啟動後，
這些 Job 會由 Spring Batch 自動執行。

這裡有幾個特性。

第一，Job 之間預設是同步執行，不是平行執行。

第二，Job 的執行順序主要由 Spring container 決定，
在原設計中沒有特別明確控制。

第三，如果錯誤沒有被妥善處理，
或是錯誤發生在 application / Bean 初始化階段，
就可能導致整個 application 結束，
進而影響後續 Job 的執行。

所以雖然這些 ETL 在邏輯上是不同的 Job，
但實際上它們仍然綁在同一個 application process 裡面執行，
並不是彼此完全獨立的任務。

## 2.4.2 Transaction 行為補充

最後補充 transaction 的部分。

在這個專案中，PQOConfig 有定義 JPA transaction manager。

所以在 Spring Batch Step 執行過程中，
如果發生 exception，Spring Batch 會 rollback 該 Step 的 transaction。

但原本設計中有一個比較需要注意的地方。
在 Reader 裡面，deleteAll() 是放在 @PostConstruct 初始化階段執行。

也就是說，
Reader 在初始化時會先 call API，
把資料放進一個 list 裡。

如果 API 回傳的資料不是空的，
程式會先執行 dao.deleteAll()，
把目標表舊資料刪掉。

後續真正的 read()，
其實只是從前面已經取得的 list 裡面，
一筆一筆把資料吐給 Spring Batch。

這裡的問題是：
deleteAll() 發生在 Reader 初始化階段，
而不是在 Step transaction 裡面，
跟後續 insert 不在一個 transaction 邊界。

所以會形成一個風險：

delete 已經先執行了，
但後面的 insert 如果失敗，
Step transaction 雖然會 rollback，
但前面已經執行的 delete 不會一起被 rollback。

這就可能造成一種狀況：

舊資料已經被刪掉，
但新資料沒有成功寫入。

也就是說，
原本的 delete 跟 insert 並沒有完整包在同一個 atomic transaction 裡面，
因此存在資料不一致的風險。

這也是這次重構中希望改善的地方之一。

3. 原系統設計特性與實際使用情境
3.1 Spring Batch 的典型能力

Spring Batch 主要是為大批次資料處理設計的。

它常見的能力包括：
chunk-based transaction、retry / skip 機制，還有 partition / parallel。

這些能力其實都很適合：

資料量很大、處理時間很長，
或者需要一定容錯能力的批次任務。

3.2 Chunk-based Transaction 概念

先講 chunk。

比較精準地說，chunk 是 Spring Batch 用來控制 transaction 邊界的單位。

例如 chunk size 設 100，Spring Batch 會持續呼叫 Reader 取得 item，
每一筆 item 經過 Processor 處理後，先暫存在目前這個 chunk 裡。

當累積到 100 筆時，才會交給 Writer 一次寫入，
接著 commit 這個 chunk 的 transaction。

所以 chunk 的重點不是「一次從來源抓 100 筆」，
而是「累積 100 個 item 後 write 並 commit」。

至於來源資料是不是分批取得，其實取決於 Reader 的實作方式。
如果 Reader 本身支援 paging 或 streaming，就可以做到真正分批讀來源資料；
但如果 Reader 一開始就把 API 資料全部抓回來，那 chunk 主要就只剩下分批 write / commit 的效果。

回到我們這個專案，資料量本身很小，
而且原本 Reader 是初始化時一次呼叫 API，把資料完整拿回來。
所以 chunk-based transaction 在這裡沒有帶來太明顯的效益。

3.3 Retry / Skip 機制

這邊再補充 Spring Batch 的 retry / skip 機制。

Spring Batch 除了 chunk-based transaction 之外，也有 fault-tolerant 的設計。
它可以針對特定 exception 設定 retry 或 skip。

比較精準地說，retry / skip 不是單純所有錯誤都重試或跳過，
而是要先定義哪些 exception 是可以 retry，哪些 exception 是可以 skip。

例如某些暫時性的錯誤，可以設定 retry；
某些單筆資料格式錯誤，如果業務可以接受，也可以設定 skip。

retryLimit 是用來限制重試上限，
skipLimit 則是限制最多可以略過幾筆資料。

如果錯誤不符合 retry 或 skip 的條件，
或者 skip 數量超過上限，
那整個 Step 還是會 fail。

所以這個機制的重點是：
在大量資料處理時，如果只有少數資料有問題，
可以避免單筆資料錯誤就讓整個批次立即中止。

不過這種設計有一個前提，
就是業務上要接受部分資料被 skip。

但在我們這個專案裡，需求不是部分成功，
而是整批成功或整批 rollback。

所以 retry / skip 雖然是 Spring Batch 很重要的能力，
但在我們這個 ETL 情境下並不適用。

3.4 差異分析

如果把 Spring Batch 提供的能力，跟這個專案實際需求拿來比，會發現：

chunk 分批 commit → 我們單一 transaction 就夠
retry / skip → 我們採整批 rollback
partition / parallel → 資料量太小，用不到

👉 可以看到，大部分能力其實都沒有用到


3.5 小結

所以這邊的小結就是：

Spring Batch 本身沒有問題，
但對這個專案來說，出現了「框架能力大於實際需求」的情況。

為了支援 chunk、retry、大資料處理等能力，
我們引入了比較多的抽象層與設計複雜度。

但實際上這個 ETL：

資料量小
不需要 retry / skip
一個 transaction 就可以完成

因此整體架構相對「過重」，也增加了維護成本。

4. 重構動機與目標
4.1 重構動機

這次重構主要有三個原因。

第一個，是架構跟需求不匹配。
因為實際流程就是 Call API、Transform、Insert DB。
但為了做這件事，要拆成 Reader、Processor、Writer，好幾層 class。

第二個，是 log 與可觀測性問題。
原本要查一次 ETL 問題，可能要同時看 CronJob、Pod、Spring Boot log、Batch log。
整個 troubleshooting 視角比較分散。

第三個，是維護成本。
原系統綁在 Spring Boot、Spring Batch、JPA、JDBC 這整套生態下，
一旦升版、dependency、CI pipeline 出問題，維護成本就會比較高。

4.2 重構目標
所以這次重構的目標，其實蠻明確的，我大概整理成五個方向。

第一個是降低維護成本。
原本的系統綁在 Spring Boot、Spring Batch、JPA 這一整套生態上，
當版本升級或 CI pipeline 出問題時，維護成本其實不低。
所以這次希望把這些不必要的框架負擔降下來，讓後續維護更單純。

第二個是簡化架構。
因為這個 ETL 的本質其實就是「Call API → Transform → Insert DB」，
但原本實作上卻要拆成 Reader、Processor、Writer 多個 class。
所以我們希望讓架構更貼近實際流程，而不是為了框架去配合設計。

第三個是提升可觀測性。
原本如果要查問題，需要同時看 CronJob、Pod、Spring Boot log、Batch log，
整個 troubleshooting 其實是分散的。
這次希望透過 Airflow，把 task 狀態、retry、log 都集中在同一個地方觀察。

第四個是統一排程管理。
以前是用 Kubernetes CronJob 做排程，
現在希望把排程、retry、監控這些能力，都集中在 Airflow 裡面處理，
讓整個 ETL 的 lifecycle 更一致、也更好管理。

第五個是提升未來的可擴充性。
因為這次的 ETL pattern 其實蠻固定的，就是 API → DB。
所以希望把共用邏輯抽出來，未來如果有新的 ETL，可以直接 reuse，
而不是每次都重寫一套新的 Batch 程式。

4.3 架構轉變

我這邊想用一個比較簡單的方式，來講這次的架構轉變。

以前我們的做法是這樣：

系統會先用 CronJob 設定好時間，
時間一到之後，就會啟動一個 Spring Boot 的應用程式，
然後再由裡面的 Spring Batch 去把整個 ETL 流程跑完，最後把資料寫進資料庫。

但現在改成 Airflow 之後，整個方式就不太一樣了。

現在是由 Airflow 去負責排程，
時間到了之後，直接執行一個 DAG 裡面的 task，
這個 task 就是一段 Python 程式，負責把 ETL 做完，然後寫進資料庫。

👉 這裡最大的差別其實是：

以前 ETL 比較像是一個「要被啟動的應用程式」，
現在則是變成 workflow 裡面的一個「任務」。

所以 ETL 的角色就變成：

👉 一個被排程系統直接執行的任務，
而不是一個需要自己啟動的應用程式。

這也是這次改動最核心的地方：

從原本比較偏 application-driven 的方式，
轉成 workflow-driven 的方式。

5. 新系統架構（Airflow DAG）

接下來這一章，我會介紹重構之後的新系統架構，也就是 Airflow DAG 的設計。
我先從檔案結構講起，這樣等一下再看圖會比較容易理解每個元件扮演的角色。

5.1 新系統整體架構

在重構之後，原本的 ETL 不再是一個獨立的應用程式，
而是被整合到 PQO-batch 這個 repository 裡面。

整個執行流程可以簡單理解成：

Airflow 會負責排程，
時間到了之後觸發一個 DAG，
DAG 裡面的 task 會去執行 ETL，
最後把資料寫進 Oracle DB。

換句話說，現在的流程是：

👉 Airflow 負責「什麼時候跑」
👉 Python task 負責「怎麼處理資料」

5.2 新系統專案結構

接著看一下新的專案結構。

整個 ETL 的實作主要集中在 app/dags 這個資料夾裡面。

裡面可以分成幾個區塊來理解：

第一類：DAG 定義（每個 table 一支）

像是：

etl_ti_proc_opt.py
etl_ti_raw_wafer_ques.py
etl_ti_wf_opt_catg.py

👉 這三支檔案，各自對應一個 ETL 任務。

以 etl_ti_proc_opt.py 為例

這支 DAG 檔，其實可以拆成四個部分來看：

第一個是 Schedule（排程）

就是在 DAG 裡面設定 cron expression，
決定這個 ETL 什麼時候執行。

第二個是 Task（任務）

這裡會用 PythonOperator 定義一個 task，
實際執行的是 pdm_api_full_load_task 這個 function。

👉 也就是 ETL 的核心邏輯入口

第三個是 Transform Logic（資料轉換）

例如 _process_ti_proc_opt_data，
負責資料清洗、欄位轉換。

第四個是 SQL Generation Logic（SQL 組裝）

像 _generate_ti_proc_opt_insert_sql，
負責把資料轉成 INSERT SQL。

👉 所以這一層可以簡單理解成：

DAG：控制排程與流程
function：負責實際資料處理

第二類：共用 ETL framework

在 pdm_api_etl_utils 裡面，有一個很重要的檔案：

👉 pdm_api_full_load.py

這是這次重構的核心。

它負責整個 ETL 的流程，包括：

呼叫 PDM API
做資料轉換
產生 SQL
控制 DELETE + INSERT transaction
寫入 log

👉 可以把它想成「ETL 的主引擎」

另外還有：

sql_utils.py：負責 SQL 值處理
schemas.py：定義 log table 的結構
utils.py：放一些共用工具，例如 DB 操作、錯誤處理

👉 所以整體設計是：

DAG 負責編排
utils / framework 負責 execution

5.3 新系統架構圖

最後用一張圖來看整體流程。

Airflow Scheduler 會去觸發 DAG，
DAG 裡面的 PythonOperator 會呼叫 pdm_api_full_load_task。

然後這個 task 會做幾件事情：

先去 call PDM API
做資料轉換
產生 SQL
控制 transaction（DELETE + INSERT）

最後把資料寫進 Oracle DB。

6. 核心實作方式

接下來這一章，我會講比較偏實作面的設計，
也就是這次 ETL 在 Airflow 上是怎麼落地的。

6.1 一表一 DAG

第一個設計是「一張表對應一個 DAG」。

也就是說，每一個 ETL 任務，都有自己獨立的一個 DAG。

像是：

TI_PROC_OPT 對應一個 DAG
TI_RAW_WAFER_QUES 對應一個 DAG
TI_WF_OPT_CATG 對應一個 DAG

👉 這樣做有幾個好處：

第一個是 失敗隔離很清楚

某一個 ETL 壞掉，不會影響其他的。

第二個是 可以單獨 rerun

如果某一張表有問題，只需要 rerun 那一個 DAG 就好。

第三個是 排程跟 retry 可以分開調整

不同 ETL 可以有不同 schedule，也可以有不同 retry 策略。

6.2 共用 ETL Framework

第二個設計是，我們沒有把三個 ETL 各自重寫一份。

而是把共通邏輯抽出來，做成一個共用的 ETL framework，
也就是 pdm_api_full_load_task()。

整個流程其實很單純：

👉 先抓資料 → 做轉換 → 產生 SQL → 刪舊資料 → 寫新資料 → 記錄 log

👉 這樣設計的好處是：

所有共同行為都集中在同一個地方管理。

所以每個 DAG 只需要關注：

👉「這張表的資料怎麼轉」
👉「SQL 長怎樣」

未來如果再新增類似的 ETL，
基本上只要複製一支 DAG，再補上 transform 跟 SQL function 就可以了。

6.3 Full Load + Atomic Transaction

第三個設計是資料寫入策略。

這邊我們沿用原本的 Full Load，也就是：

👉 先 DELETE，再 INSERT

但這次有特別強調一件事：

👉 整個過程要包在同一個 transaction 裡面

也就是：

刪除成功、插入也成功 → 才 commit
只要中間有任何一步失敗 → 就全部 rollback

👉 這樣可以確保資料不會出現：

刪掉了，但新資料沒寫進來
或是只寫了一部分資料的狀況

換句話說，就是保證資料的一致性。

6.4 Airflow Retry 機制

再來是 retry。

在原本的 Spring Batch 裡，其實沒有明確用 retry / skip。

但在 Airflow 裡，我們可以直接在 task level 設定 retry。

像這裡設定：

最多 retry 5 次
每次間隔 10 秒
並且會做 exponential backoff

👉 這樣的好處是：

如果遇到像 API 暫時 timeout、或網路不穩這種「暫時性問題」，
Airflow 會自動幫我們重試，不需要人工介入。

不過這裡要注意，Airflow 的 retry 是 task-level retry。

也就是說，如果這個 task fail，Airflow 會重新跑整個 ETL task，
不是像 Spring Batch retry / skip 那樣，只針對單一 item 做 retry 或 skip。

所以這邊的 retry 比較適合處理 API timeout、網路不穩這種暫時性問題。

6.5 ETL 控制與績效記錄

除了 Airflow 自己的 log 之外，
我們還額外寫了兩張 DB log table。

第一張是 PERF_LOG

主要記錄整個 ETL 的執行情況，例如：

跑多久
處理幾筆資料
成功或失敗

第二張是 CTRL_LOG

這張比較偏錯誤細節，會記錄：

哪一筆資料出錯
錯在哪裡
error code 是什麼

👉 這樣的好處是：

即使不看 Airflow log，
也可以直接從 DB 查到 ETL 的執行情況與錯誤資訊。

6.6 小結（流程）

最後用一個流程來總結整個 ETL 的執行方式。

整體流程是這樣：

一開始先 call API，
如果沒有資料，就直接寫一筆 perf log 結束。

如果有資料，就會進入：

👉 transform → 產生 SQL → 開 transaction

接著會先做 DELETE，
如果 DELETE 失敗，就會：

👉 寫 ctrl log → rollback → 寫 perf log → task fail

如果 DELETE 成功，就會做 INSERT，
如果 INSERT 過程中有任何一筆失敗，也會走同一條錯誤流程。

只有在全部 INSERT 成功的情況下，才會 commit，
然後寫 perf log，整個流程才算完成。

👉 所以整體可以理解成：

正常流程走 commit，
錯誤流程全部集中 rollback + logging。

所以整個設計的重點，就是把正常流程跟錯誤流程都明確定義出來，並確保資料一致性。

7. 設計亮點與實際收益
7.1 架構簡化

第一個很直接的收益就是架構簡化。

原本的 Spring Boot application、Spring Batch Job / Step 組裝、
Reader / Processor / Writer、JPA entity / repository 依賴，現在都不需要了。

也就是說，我們把很多「為了框架而存在的結構」拿掉了，
讓程式更貼近實際需求。

7.2 維護成本下降

第二個是維護成本下降。

不是說 Airflow / Python 就完全沒有 CI 或 dependency 問題，
因為 DAG parsing、provider 相容性、pipeline 還是可能要修。

但相較於原本 Spring Boot 版本，
現在少掉了很多應用框架層級的建置、打包與升版負擔。
維護焦點會更集中在 DAG 跟 ETL 邏輯本身。

7.3 可觀測性提升

第三個是可觀測性提升。

現在透過 Airflow UI，可以直接看到：

DAG 有沒有成功
哪個 task fail
retry 幾次
log 是什麼

查問題會直覺很多。

7.4 可擴充性提升

第四個是可擴充性提升。

這次把共用流程抽成 framework，
所以未來若有更多類似 PDM API 到 Oracle 的 ETL，
可以比較快地複製與擴展。

7.5 Failure Isolation（失敗隔離）

第五個是 failure isolation。

如果錯誤是發生在 Step 裡，而且有被 Spring Batch 正常處理，
不一定會讓整個 application 中斷。

但如果是未處理的 exception，或是發生在 application 初始化階段，
就有可能讓整個 application 中斷，進而影響後續 Job。

所以我這邊會說，原本多個 ETL Job 不是完全隔離，
它們還是綁在同一個 application process 裡。

8. Trade-off 與設計取捨
8.1 SQL 執行策略：row-by-row

第一個 trade-off 是 SQL 執行策略。

目前採用 row-by-row，也就是逐筆執行 INSERT SQL。

原因很簡單：資料量小、邏輯直觀，
也方便記錄單筆錯誤與 control log。

但代價就是 DB round trip 會比較多。
如果未來資料量明顯增加，就可以評估 batch insert、parameterized SQL 或 executemany。

8.2 資料同步策略：Full Load

第二個 trade-off 是資料同步策略。

目前採用 Full Load，也就是 DELETE + INSERT，而不是 incremental load。

原因是 API 現在只提供全量資料，沒有提供 update timestamp 或 CDC。
如果硬做 incremental，反而要自己比對 diff，系統會更複雜。

所以在目前這個條件下，Full Load 其實是比較合理、也比較穩定的做法。
未來如果 API 能提供變更追蹤資訊，或者資料量顯著增加，再來考慮 incremental load 會比較有價值。

8.3 DAG 設計：單 task 模式

第三個 trade-off 是 DAG 設計。

目前每個 DAG 只有一個 PythonOperator，也就是單 task 模式。

這樣做的原因是，現階段流程很單純：
單一 API、單一 table、沒有中間層，也沒有複雜的 downstream dependency。

如果現在就把 DAG 拆成很多 task，
反而會增加 task 間資料傳遞、DAG 複雜度，以及 transaction 邊界管理難度。

但如果未來流程變複雜，例如加入 data validation、stage table、notification、data quality check，
那就可以再拆成 extract、transform、load、notify 等多個 task，
進一步提升可觀測性跟錯誤隔離能力。

9. 重構前後比較

如果用一句話總結這張比較表：

原本是 CronJob 啟動應用程式，
現在是 Airflow 直接執行任務。

技術棧從 Java / Spring Boot / Batch / JPA，
變成 Python / Airflow。

架構複雜度下降，維護成本下降，可觀測性由分散變集中。
retry 管理也從原本不明確，變成 Airflow 內建。
release unit 也從原本比較分散，變成集中在 batch repo 與 DAG。

10. 結論
10.1 本次重構帶來的效益

最後做個總結。

這次重構成功把原本 PQO-PDMEtl 的 ETL 流程，從 Spring Batch 架構搬到 Airflow DAG。
這次改造真正的價值，不只是技術棧從 Java 變 Python，
而是把 ETL 從「應用程式導向的批次程式」，轉成「排程系統導向的資料流程」。

這次重構帶來的效益包括：

維護成本下降、架構簡化、可觀測性提升、排程與任務管理整合、
同時保留既有 Full Load 與資料一致性策略，也提升了未來擴充與複用能力。

10.2 最後總結

所以對這種：

資料量小、Full Load、流程單純，而且需要排程與監控整合的 ETL 任務來說，
我認為 Airflow DAG 比 Spring Batch 更符合實際需求，
也更適合作為部門內類似批次任務的實作模式。

我的分享大概到這邊，謝謝大家。
